# 证据与判断

以下是取证方法和判断示例。它们不是当前 PR 的状态报告，也不是每次都要执行的检查清单。

## 选择验证路径

围绕当前修改选择少量有区分力的用例。保留相关调用的真实行为，清楚标记替代的依赖或构造的输入。

| 修改类型 | 优先检查 | 证据边界 |
| --- | --- | --- |
| 匹配、清理、脱敏 | 完整值、替换符、相邻普通文本、导出读回 | 符合某个地址或字符串标准，不代表在任意文本中都应该删除 |
| 性能、批量读取 | 相同输入的选中行和顺序、批次边界、乱序子集、相关空值或嵌套字段 | 区分正确性、调用次数、耗时和峰值内存；不要互相替代 |
| 去重、合并状态 | 保留规则、相关输入顺序、跨组连接、实际算子运行 | 数学连通结果一致，不证明递归深度、状态生命周期或执行成本一致 |
| 音视频输出 | 输出可读取、相关帧或包内容、时间戳、对应流、实际调用方 | 声明一个音轨不等于写入了声音；包数相同也不单独证明内容正确 |
| 测试专用 PR | 实际收集、真实调用、断言能否发现合理的错误实现 | 在必要时用小型 mutation 或调用参数检查；不要一律要求大量故障注入 |
| 恢复、懒执行、Ray | 延迟消费、复用实例、恢复到导出的完整链路 | 注入逻辑 OOM 不证明物理 GPU 恢复，构造回归不证明生产发生频率 |

### Data-Juicer 本地验证

- 先读实际 CI 配置和 `tests/run.py`，确认标签、文件映射与测试发现方式。
- 独立 worktree 复用现有环境时，显式核对 `sys.executable`、模块 `__file__` 和工作目录。可用 `uv run --active --no-sync python ...`，并在确有需要时设置 `PYTHONPATH`。这些参数不证明导入正确，仍要检查实际路径。
- GitHub API 取得的精确文件，配合本地框架运行，是局部版本验证。不要把它称作完整 head checkout 的全套验证。
- 如果有动态模块、替代检测器或固定画面转换，说明哪些路径是真实的，哪些算法没有验证。不要把测试装配错误写成 PR 缺陷。
- `git fetch` 失败时，可用可用的 GitHub 工具读取 metadata、patch 或原始文件。文件读取成功不代表测试或 CI 已通过。
- 性能用例应比较同一数据、参数和环境，区分作者结果与独立复测。无需为普通小修改重建作者的完整基准。

## 判断示例

### 有效但含义模糊的字符串

PR 支持常见压缩 IPv6。常见地址与替换功能已验证，但单独的 `::` 没有被清理。

先检查目标、实际数据影响和普通文本中的歧义。`::` 是有效地址这一事实，本身不足以决定阻塞。可以记录为非阻塞范围讨论，或按用户决定不提出。如果 PR 明确承诺了此项且后果重要，需要重新评估。

### 顺序改变导致实际崩溃

去重优化改为边扫描边合并。相同文本搭配降序 UID 时，旧实现正常保留最小 UID，新实现因递归查找长链而崩溃。

这是有前后对比的有效输入回归，适合 Request changes。评论应说明输入规模、顺序、真实入口和异常。迭代查找可以作为建议，但作者可以选择其他正确方案。不要声称生产中经常发生，除非有额外证据。

### 批次读取保持顺序

性能 PR 改为分批读取字段。相关测试通过，跨批次和乱序子集的选中行、顺序及导出一致，解码调用减少。

这些证据支持代码层面的批准。作者报告的大规模内存或吞吐收益仍应标明来源。必要 CI 尚未完成时，结论是 Approve 后等待 CI。

### 原问题已修复，旧 review 仍未更新

作者新增了修复提交，而 GitHub 仍显示此前的 Changes requested。

先复测当前 head。旧 review 状态不证明缺陷仍在。原问题解决后更新维护判断；不要顺势把不相关建议升级为新的阻塞。

### 当前只有本地证据

本地测试通过，格式检查通过，但远端单元测试等待环境审批。

分别报告这些状态。不要用本地通过替代远端 CI，不称 PR 已满足合并条件。只有在授权范围内才放行环境、重跑任务或合并。

### 用户只问怎么回复

给可直接使用的评论。不要擅自发布 review，不增加冗长审查报告。若用户已明确要求“把这条发到 PR”，则核对身份与目标后完成发布，不重复索要相同授权。

## 评论示例

### Approve

> LGTM, thanks for your work!

### Request changes

> Thanks for the optimization! With [specific valid input], the base version [expected result], but the current PR [observed failure] through [actual entry point]. Could you address this and add a regression test?

仅在原因已确认时补充一两句机制解释。不要把“可能”写成已复现事实。代码片段或复现脚本较长时，放在折叠区域或单独链接，不遮住核心请求。

### 作者提供修复后

若本地已验证修复，且没有必要补充说明，使用简短批准即可。若还有 CI 门槛，把等待状态告诉用户，不必把所有本地检查复制到公开评论。
